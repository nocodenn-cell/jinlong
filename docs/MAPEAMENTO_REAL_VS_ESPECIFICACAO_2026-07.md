# Mapeamento: Sistema Real vs. Especificação

**Data:** 2026-07-01. **Método:** comparação direta de código (`pdv-importados/`, `pdv-local/`, `backend/supabase/`) contra a especificação funcional identificada no repositório, com verificação pontual de arquivo/linha para cada afirmação — não é uma leitura superficial dos dois lados, é checagem cruzada.

## 0. Qual documento foi tratado como "a especificação" — e um achado antes de qualquer comparação

Não havia especificação anexada nesta conversa. Por instrução explícita, uma varredura foi feita no repositório, issues, PRs e comentários antes de assumir qualquer coisa. Resultado da varredura:

- **Não existe PRD/especificação de negócio tradicional no repositório principal.**
- **Existe, porém, uma especificação real e estruturada**: `docs/plano-mestre/` — 8 documentos (`README.md`, `01-ARQUITETURA.md`, `02-DESIGN-SYSTEM.md`, `03-PADROES-UX.md`, `04-MODULOS.md`, `05-ARQUITETURA-PDV.md`, `06-CONTRATO-DE-EVENTOS.md`, `07-MAQUINA-DE-ESTADOS-PDV.md`), que se autodeclara **"fonte única de verdade"** para arquitetura, design system, UX e regras de negócio por módulo. O Pilar 4 (`04-MODULOS.md`) é literalmente uma especificação funcional por módulo (objetivo, regras de negócio, fluxos, permissões, integrações, auditoria).

**Achado zero, antes de comparar qualquer módulo:** essa especificação **não está no branch principal**. Ela existe apenas no **PR #121** (`docs(plano-mestre): documentação canônica em 4 pilares`), **aberto, em draft, não mergeado**, na branch `claude/fastproduct-architecture-design-exd2zz`. Ou seja: a especificação mais completa e formal que este sistema possui **não faz parte do que está de fato entregue** — é, ela própria, um artefato "apenas na intenção" no sentido mais literal possível. Este documento usa o conteúdo do Plano Mestre como referência (é a melhor fonte disponível e tecnicamente sólida), mas o fato de ele não estar mergeado é, por si, o primeiro item da seção 4 (divergências estruturais graves).

Um segundo achado zero: o Plano Mestre cita `docs/adr/ADR-PDV-tema-escuro.md` (referenciado como "ADR-PDV-002") como uma decisão formal já tomada ("tema escuro do PDV foi **rejeitado**"). **Esse arquivo não existe.** `docs/adr/` contém apenas `ADR-PDV-centro-de-gravidade.md` (verificado por listagem direta). A especificação cita uma decisão registrada que não está registrada em lugar nenhum — é uma afirmação de fato sem o fato.

## 4. Divergências estruturais graves

1. **A especificação mais completa do sistema não está mergeada.** O Plano Mestre (`docs/plano-mestre/`) — que se autodeclara fonte única de verdade — vive inteiramente no PR #121, aberto e em draft. Ninguém que clona `main` hoje tem acesso a ela. Uma especificação que não está no branch principal não está, na prática, em vigor — é uma proposta de especificação.
2. **A especificação cita uma decisão arquitetural registrada que não existe.** `ADR-PDV-tema-escuro.md` (ADR-PDV-002) é referenciado como decisão **já tomada e rejeitada**, mas o arquivo não existe em `docs/adr/`. Isso é mais grave do que uma lacuna de conteúdo: é uma afirmação de proveniência (existe um ADR, foi decidido, foi rejeitado) sobre algo que não tem registro nenhum. Se alguém confiar nessa citação para justificar não trabalhar em tema escuro, estará confiando em uma referência fantasma.
3. **Documentação interna já se contradiz sobre o mesmo fato, na mesma data.** `AUDITORIA_PAINEL_ADMIN.md` (2026-06-05) afirma "9/17 rotas migradas, Fase 9 pendente"; `ADMIN_PANEL_GUIDE.md` (mesma data, 2026-06-05) afirma "Fase 9 Completa — 13 rotas". A contagem real hoje é 12 pastas de rota em `app/admin/`. Três números diferentes (9, 12, 13) para a mesma pergunta ("quantas rotas admin existem?"), nenhum deles gerado com má-fé, mas isso significa que **nenhum desses documentos pode ser confiado como fonte de verdade sem verificação direta no código** — o que é exatamente o oposto do que documentação deveria oferecer.
4. **A especificação subestima o que já existe (Fiscal) e superestima o que não existe (Variações de produto), e erra a localização de uma feature real (Etiquetas).** Isso não é um problema de "documentação desatualizada" trivial — é sintoma de que a especificação foi escrita sem uma varredura completa do código real no momento da escrita, o mesmo tipo de erro que este próprio documento tentou evitar fazendo verificação direta antes de cada afirmação.
5. **O "gate financeiro de produção" (5 testes obrigatórios, "regra binária sem exceções") não tem automação encontrada em CI.** Um documento que se descreve como bloqueante ("sem exceções") mas cuja execução real não está amarrada a nenhum pipeline é, na prática, uma política de honra — o oposto do que a seção de autoimposição da revisão anterior já havia identificado como padrão geral do repositório.
6. **O plano de feature flags foi parcialmente implementado por um caminho que viola a própria arquitetura em camadas do sistema.** A intenção (`FEATURE_FLAGS_PLANO.md`) previa API route + hook; o que nasceu (`FeatureToggle.tsx`) é uma chamada direta ao Supabase dentro de um componente client — já identificado na revisão anterior como uma das duas únicas violações confirmadas de Frontend pulando direto para Infrastructure. Ou seja: quando a intenção documentada foi contornada, foi contornada na direção arquiteturalmente pior, não na melhor.

## 5. Riscos de produção imediata

Cruzando esta comparação com os achados já verificados nas duas auditorias arquiteturais anteriores (`PRINCIPAL_ARCHITECT_REVIEW_2026-07.md`, `PRINCIPAL_ARCHITECT_FINAL_VALIDATION_2026-07.md`), os riscos que **este** mapeamento específico adiciona ou reforça com evidência nova:

1. **Confiar na especificação como se fosse o comportamento real é perigoso hoje.** Qualquer decisão de produto ou onboarding de desenvolvedor baseada em `04-MODULOS.md` sozinho vai errar pelo menos duas vezes de forma concreta (Fiscal subestimado, Etiquetas mal localizado) — isso não é risco hipotético, é erro já demonstrado nesta própria checagem.
2. **O gate financeiro "sem exceções" não tem enforcement mecânico.** Se a promessa do documento é real ("regra binária, sem exceções"), e a execução depende de alguém rodar manualmente, existe uma janela real de release sem o gate ter sido de fato executado — sem qualquer sinal disso no pipeline de CI.
3. **A ADR fantasma (`ADR-PDV-tema-escuro.md`) pode ser citada para justificar decisões de produto** (por humano ou por agente futuro) que na verdade nunca foram formalmente registradas — isso é um vetor de decisão baseada em uma referência que não resiste a uma checagem de dois segundos, exatamente o tipo de erro que só aparece quando finalmente vira relevante (ex.: um cliente pergunta "por que vocês decidiram X" e a resposta aponta para um arquivo que não existe).
4. **Duas fontes de verdade sobre o estado do painel admin (Fase 9) continuam sem reconciliação.** Isso já foi sinalizado nas revisões anteriores como risco de manutenção; aqui fica confirmado como risco de **produção imediata** porque afeta diretamente onde um desenvolvedor vai procurar (e não vai encontrar) uma rota ao corrigir um bug relatado por um usuário em `/admin/clientes` — que não existe.
5. **A especificação viva mais completa do sistema depende de um PR draft não mergeado permanecer disponível.** Se essa branch for deletada, rebaseada de forma destrutiva, ou o PR for fechado sem merge, a "fonte única de verdade" do projeto desaparece sem que isso apareça em nenhum lugar do `main`. Isso deveria ser corrigido antes de qualquer coisa mencionada nas seções anteriores — é o risco mais barato de eliminar (mergear o PR, ou pelo menos mover o conteúdo para um lugar persistente) e o mais caro de ignorar.
