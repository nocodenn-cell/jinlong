**Não executar sem autorização específica.** Objetivo: alinhar o histórico main × produção. O check `migration-remote-drift` (agora apontado para produção) lista esta versão como bloqueante (`remote_ausente`).

## Por que é no-op

A migration só faz `ALTER TABLE public.pdv_config ALTER COLUMN gerente_senha_sha256 DROP NOT NULL`, e só se a coluna existir e for `NOT NULL` (guard em `information_schema`). Em produção **a coluna não existe**, então nada no schema muda. Aplicar só grava a versão no ledger.

## 1. Pré-checagem (somente leitura)

```sql

  NOT EXISTS (SELECT 1 FROM supabase_migrations.schema_migrations WHERE version = '20261022020000') AS ainda_nao_registrada,
  NOT EXISTS (SELECT 1 FROM information_schema.columns
              WHERE table_schema = 'public' AND table_name = 'pdv_config' AND column_name = 'gerente_senha_sha256') AS coluna_ausente_noop;
```

Prosseguir só se as duas forem `true`. Em 2026-10-28 14:04 UTC eram.

## 2. Backup

## 3. Aplicação

Uma transação, que:
